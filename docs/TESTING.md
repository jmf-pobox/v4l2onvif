# Testing v4l2onvif

This document is the complete testing strategy for the fork. Read it in
full before writing any code or tests.

Testing an ONVIF server is harder than testing a library — it spans
SOAP/HTTP, WS-Discovery multicast, RTSP, V4L2 ioctls, and gSOAP-generated
serialization. The strategy is to isolate each layer and add adversarial
clients we can run in CI.

The session this strategy was written against (2026-06-06/07) had us
patching the server live, restarting it, and asking the user to retry in
Win11 to confirm each fix. Six bugs were found this way — every single
one of them is reproducible in a sub-second unit or integration test.
The whole methodology below exists so the next session doesn't repeat
that loop.

## What We Are Testing

The daemon does four things, each of which has its own failure modes:

| Subsystem | Failure modes from this session |
|-----------|--------------------------------|
| WS-Discovery responder | Multicast join on wrong interface; XAddr advertises wrong host IP |
| ONVIF SOAP server | `ReferenceToken` > 64 chars; missing `Framerate`; missing `RTP_TCP` capability flag; pixel-format match misses `V4L2_PIX_FMT_MJPEG`; over-populated optional sub-configurations; bare `std::string` corruption (TZ field) |
| V4L2 capture & probing | `getFormat` called with the ONVIF token instead of the device path |
| RTSP server (live555) | Reports `192.168.20.105` (wifi IP) instead of the per-client IP |

Every entry above is a test we now must have.

## Layer 1: Unit Tests (Catch2)

Pure logic with no side effects, no network, no real V4L2. Highest-value,
lowest-cost testing.

### What to test (and the bug each blocks)

| Function | Test | Bug it blocks |
|----------|------|---------------|
| `ServiceContext::resolveDevicePath` | Token without entry → returns token unchanged; token with entry → returns device path | Yesterday's token-as-path crash in `getFormat` |
| `ServiceContext::getLocalIp` env override | `V4L2ONVIF_IP=192.168.122.1` → returns that; unset → returns gethostname fallback | Win11 advertised the wifi IP, unreachable from the VM subnet |
| Pixel format → ONVIF encoding | `MJPG` and `JPEG` both map to `tt__VideoEncoding__JPEG` | `getVideoEncoderCfgOptions` skipped MJPG entirely |
| ReferenceToken length invariant | Every token generated by the server is ≤ 64 chars | Win11 silently rejected `/dev/v4l/by-id/...` tokens |
| Profile builder | Returned `tt__Profile` has `Name`, `VideoSourceConfiguration`, `VideoEncoderConfiguration` populated; PTZ / Analytics / Metadata are `NULL` for webcam | Empty `<tt:Name/>`, empty PTZ/Analytics subtrees → Win11 stopped at GetVideoEncoderConfigurationOptions |
| `getVideoSourceCfg` | Returned config has `Name`, `Bounds.width > 0`, `Bounds.height > 0` for a valid device | Empty Name, zero Bounds |
| StreamingCapabilities builder | `RTP_TCP` and `RTP_RTSP_TCP` both `true` in both the device-level and per-service Media capability responses | Two locations needed patching; one missed = Win11 ignores streaming |
| GetSystemDateAndTime TZ field | TZ assigned from a literal or sanitized string, never from a potentially-corrupted `m_timezone` | `std::bad_alloc` crash on the third request |

### How to make legacy code testable

The upstream code mixes pure logic with V4L2 ioctls and gSOAP allocator
calls. To test:

- **Extract pure functions** from `onvif_impl.cpp`. The token-to-device-
  path resolver is one. Pixel-format → ONVIF-encoding is another. The
  URL builder is a third.
- **Inject the V4L2 layer** with a function pointer or strategy class.
  Tests pass a fake `getFormat` that returns fixed values; production
  passes the real V4L2-ioctl version.
- **Construct gSOAP structs without a `soap*` context** for the small
  pure parts. Where we must use `soap_new_*`, pass a per-test `soap*`
  created with `soap_new()` in the fixture.
- **One test file per source file:** `tests/unit/test_onvif_impl.cpp`,
  `tests/unit/test_server_media.cpp`, etc.

### How to run

```bash
cmake --preset debug
cmake --build build
ctest --test-dir build --output-on-failure        # all tests
ctest --test-dir build -R test_onvif_impl          # one test file
ctest --test-dir build -R "ReferenceToken"         # by test name
```

## Layer 2: Integration Tests

Multiple subsystems together, but deterministic. The server runs as a
child process bound to `127.0.0.1` on test-only ports. The test drives
it as a SOAP client.

### Two driver options, by purpose

- **`onvif-client.exe`** (already built by `make`) — easiest path. The
  client speaks real ONVIF over the wire and writes its output to stdout.
  Tests fork-exec it with specific arguments and assert on stdout / exit
  code. Good for happy-path coverage.
- **Hand-built SOAP requests via libcurl + assertions on the response
  XML** — needed for tests that exercise *malformed* or *Win11-specific*
  request patterns the client wouldn't emit. We have captured pcaps from
  this session under `.tmp/soap*.txt` that document Win11's exact wire
  format; those become the input fixtures.

### What to test

| Scenario | Assertion |
|----------|-----------|
| WS-Discovery probe → ProbeMatches | Server replies with `NetworkVideoTransmitter` scope and reachable `XAddrs` |
| Full SOAP discovery sequence | `GetCapabilities` → `GetProfiles` → `GetStreamUri` all succeed and the returned RTSP URL is reachable |
| ONVIF Profile S checklist | Every method in the Profile S minimum set returns SOAP-valid XML, never a fault |
| Win11 wire-format fixtures | Replay `.tmp/soap*.txt` captured this session, assert each response matches the schema |
| Multi-interface multicast | Bind two veth pairs; server must receive probes on both |
| Crash regression | Send 100 sequential `GetSystemDateAndTime` requests; the server must not crash, leak, or OOM |

### Fixtures

- **Synthetic V4L2 device** via `v4l2loopback` kernel module. CI loads
  the module, creates `/dev/video99`, and feeds it a test pattern from
  `gst-launch`. The server runs against `/dev/video99` — no real camera
  needed.
- **Per-test soap context** to isolate gSOAP allocator state.
- **Captured pcaps from this session** under `tests/fixtures/win11/`
  (we'll commit selected captures from `.tmp/soap*.txt`). These are the
  canonical "what Win11 actually sends" reference.

### How to run

```bash
ctest --test-dir build -L integration              # integration only
ctest --test-dir build -R test_get_profiles         # one scenario
```

## Layer 3: Protocol Compliance

Drive the server with multiple real clients and assert each gets the
result it expects. Slower than L2, but catches client-specific quirks
(this is where Win11's `MS-WebServices/1.0` weirdness lives).

### Clients to run in this layer

- **`onvif-client.exe`** — our own
- **`gst-launch` with `onvifsrc`** — gstreamer's ONVIF client
- **`python-onvif-zeep`** — Home Assistant's library; the canonical
  reference for "does it work with a real ONVIF consumer"
- **`onvif-cli`** (npm package) — what some home automation users run
- **The Win11 path** — manual, gated, only after every L1+L2+L3 above
  passes locally

Each client gets its own test binary that exercises a fixed scenario
and asserts pass/fail. Failures here always point at WSDL cardinality
or namespace bugs.

## Layer 4: Manual / Win11

This is the layer that bit us this session. It's the slowest, hardest
to reproduce, and weakest signal. **It is no longer the first place we
look.** Win11 is a smoke check on a build that has already passed
L1+L2+L3.

The Win11 checklist (run only after L1–L3 are green):

1. Boot the win11 VM (NAT on virbr0).
2. Start the server: `onvif-server.exe -H 8080 -R 8554 -i /dev/v4l/by-id/...`.
3. Win11 Settings → Bluetooth & devices → Cameras → Add a network camera
   → Search.
4. Camera should appear; Add it (admin/admin if asked — we ignore creds).
5. Open Camera app; preview should be live within ~5 s.
6. Open Zoom → Settings → Video; the camera should appear in the dropdown
   and produce frames.

If any step fails, **a new L1 or L2 test must reproduce the failure**
before any code is touched. The session lesson: every bug that bit Win11
was reproducible in a deterministic test we hadn't written.

## Sanitizers

Every test runs under both Debug and ASan + UBSan presets in CI. MSan
and TSan are periodic deep checks, not per-PR.

| Sanitizer | What it catches | Builds |
|-----------|-----------------|--------|
| AddressSanitizer | Buffer overflows, use-after-free, double-free, heap corruption | `build-asan/` |
| UndefinedBehaviorSanitizer | Integer overflow, null deref, alignment, shift errors | `build-asan/` |
| ThreadSanitizer | Race conditions (the wsdd thread + SOAP handler thread are a known race risk) | `build-tsan/`, periodic |
| MemorySanitizer | Read of uninitialized memory | clang only, periodic |

`make check` runs Debug + ASan + UBSan. CI matches.

## Test Priority for the Backfill

The patches landed this session need their regression tests. In order
of value:

1. **`resolveDevicePath` unit test** — protects every V4L2 ioctl helper
   from a future refactor that breaks the token→path mapping.
2. **ReferenceToken length invariant** — single-line property test, runs
   on every Profile generated.
3. **`getVideoEncoderCfgOptions` pixel-format coverage** — the MJPG/JPEG
   parity bug. Drive with three formats (YUYV, MJPEG, H264), assert each
   gets the right ONVIF encoding.
4. **GetCapabilities streaming flags** — both per-device and per-service
   responses; lock both to `RTP_TCP=true`, `RTP_RTSP_TCP=true`.
5. **GetVideoSources Framerate** — must be > 0 for any source that has
   a discoverable frame rate.
6. **GetProfiles structure** — no empty `<tt:Name/>`, no empty PTZ/
   Analytics/Metadata subtrees for webcam-class devices.
7. **L2 round-trip with `onvif-client.exe`** — Discovery → Profile →
   StreamUri → ffprobe the URL; asserts the entire happy path end-to-end.
